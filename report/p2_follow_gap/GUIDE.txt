PART 1. PROJECT CONTEXT
---------------------------------------------------------------------

1.1 The overall project
- A group project on autonomous racing with a 1:10-scale RoboRacer /
  F1TENTH car on the Porto track.
- Five topics, one per person:
    P1  Pure Pursuit (geometric path tracking)
    P2  Follow-the-Gap (reactive LIDAR driving)        <-- YOU
    P3  Track representation / reference centreline (spline, curvature)
    P4  Evaluation protocol and statistics (CSV schema, box plots, CIs)
    P5  Deep RL baselines (PPO and SAC from Stable-Baselines3)
- The report's central claim is a comparison between methods, based on
  about 5 runs per method (small samples, so honest statistics matter).

1.2 The two simulators
- f1tenth_gym: pure-Python simulator, CPU only, runs much faster than
  real time. Used for ALL development, tuning and training.
  Your install is the OLD API: package f110_gym 0.2.1, gym 0.19.0,
  4-value returns from reset() and step(), timestep 0.01 s per step.
- AutoDRIVE: Unity-based high-fidelity digital twin, needs a GPU, runs
  in REAL TIME only, only the Porto track, run CENTRALLY (you request
  slots and recordings, you do not run it yourself). Gives a 1080-beam
  270-degree LIDAR, IMU, encoders, odometry, camera. Accepts normalised
  throttle and steering. Simulator time is the scarcest resource.
- Rule: build and tune in f1tenth_gym, then move the finished method to
  AutoDRIVE with NO CODE CHANGES (only config/parameter changes).

1.3 What P2 is
- Follow-the-Gap drives using ONLY the current LIDAR scan: no map, no
  centreline, no memory of the lap.
- Algorithm:
    1. Clean the scan (clip far values, smooth, fix NaN/inf).
    2. Find the nearest obstacle, blank a "safety bubble" around it.
    3. Find the widest run of free beams (the gap).
    4. Steer toward the middle of that gap.
    5. Speed from the same scan: slower when steering hard and when the
       range ahead is short.
- A reference implementation exists in the repository (starting point).
- THE REAL SUBSTANCE: the widest gap is not always the right direction.
  Somewhere on Porto the rule will pick an opening that is wide in the
  scan but wrong on the ground (past a corner, or on the outside of a
  hairpin). You must find those cases, explain what the rule got wrong,
  repair it, and show the repair did not cost lap time elsewhere.

1.4 Your objective (from the problem statement)
  Complete clean laps using only the current scan, and characterise
  where the widest-gap rule selects the wrong direction on this track.

1.5 Your four deliverables
  D1  Gap selection verified offline on saved scans: the returned
      heading points into visibly free space.
  D2  One full lap of Porto in f1tenth_gym without collision, with
      scan-derived speed regulation.
  D3  Three consecutive clean laps in AutoDRIVE with NO code changes.
  D4  Two documented failure cases (the scan, the wrong choice, the
      repair) and lap results submitted.

1.6 Reference
  V. Sezer and M. Gokasan, "A novel obstacle avoidance algorithm:
  Follow the Gap Method," Robotics and Autonomous Systems, 60(9), 2012.

1.7 Dependencies on teammates (you are about 90% independent)
  - P3 centreline: OPTIONAL. Only helps to analyse failures (compare
    chosen heading to track direction).
  - P1, P5: none.
  - P4 CSV schema: needed when you log final results (week 2 onward).
    Until agreed, log in your own format and convert later.
  - Shared controller interface: agree once, early.
  - AutoDRIVE slots: your one real external dependency. Book early.

PART 5. THE CONTROLLER INTERFACE AND KEY FORMULAS
---------------------------------------------------------------------
Interface (agreed with team):  steer, speed = controller.act(scan, pose=None)
  - scan: array of 1080 ranges in metres, 270 degrees, index 540 is
    straight ahead, index 0 is the right-most beam (-135 deg),
    angle increases to the left.
  - steer: radians, positive = left (check sign in AutoDRIVE mapping).
  - speed: m/s (the sim wrapper converts to normalised throttle).
  - FTG ignores pose; it must work from the scan alone.

Formulas:
  angle(idx)      = -135 deg + idx * (270 / 1079)
  bubble half-width (beams) = ceil( atan(bubble_radius / nearest_dist)
                                    / angle_per_beam )
  steer           = clip(steer_gain * angle(target_idx), -max_steer, max_steer)
  speed           = clip(k_range * front_range - k_steer * |steer|,
                         speed_min, speed_max)
  front_range     = minimum range in the central +-15 degree cone

Control rate: the gym steps at 100 Hz. Repeat each command for 5 steps
so the controller runs at 20 Hz, the rate used in AutoDRIVE and RL.

=== WEEK 3: Failure analysis and repair (D4 analysis) ===  16-20 h

Days 1-2 (about 6 h) - find the bad moments
 1. Write tools/find_bad_moments.py. Load a run .npz and flag steps with:
      a. Collision (keep the 2 seconds BEFORE it: the bad decision
         happens earlier than the crash)
      b. Near-miss: minimum range in the forward +-60 deg below 0.3 m
      c. Steering flip: steer changes sign within a few steps
         (left-right-left = two gaps competing)
      d. Very low speed for many steps (stuck/hesitating)
      e. If P3's centreline is ready: chosen heading differs from the
         track direction by more than about 40 deg, or lateral
         deviation spikes
 2. Provoke failures deliberately:
      - spawn at 8-10 different places (before every corner/hairpin)
      - raise speed slightly
      - vary bubble_radius (small bubbles show failures big ones hide)
      - replay saved scans offline: which gap does the rule pick and
        is it right? A wrong choice does not need a crash to be found.

Days 3-4 (about 5 h) - classify and pick two cases
 3. Plot every flagged moment with plot_scan.py. For each ask:
    "Is the arrow pointing where the track actually continues?"
      NO  -> gap-selection failure: it counts for your analysis
      YES -> speed or bubble problem: tune it and move on
 4. Choose TWO clear gap-selection failures (likely: a wide opening
    past a corner, and the outside of a hairpin). For each, write:
      - Where on the track (coordinates / corner name)
      - The scan plot (save in data/plots/)
      - What the rule picked and WHY (widest run of free beams)
      - What was actually correct (where the track continues)
      - The proposed repair

Days 5-7 (about 7 h) - repair and compare
 5. Implement the repair in ftg_repaired.py with its own
    follow_gap_repaired.yaml. Pick based on what you observed:
      - score gaps by depth AND width, not width alone
      - steer toward the deepest beam in the gap instead of its centre
      - penalise gaps requiring a big steering change vs the last one
      - disparity extender, or a bigger bubble in corners
      - apply the fix conditionally (only when the failure pattern is
        detected)
 6. Write NEW unit tests that reproduce your two failure scans: the
    baseline must fail them, the repaired version must pass them.
 7. Run both versions on the SAME start poses and the same conditions,
    at least 5 runs each. Compare lap time and collisions.
 8. If the repair slows laps elsewhere, retune or make it conditional.
 9. Commit and tag: git tag ftg-repaired-v1.
End of week 3: two documented failures, repaired controller, before/after
numbers.

PART 7. HOW TO DETECT "THE RULE CHOSE WRONG"
---------------------------------------------------------------------
Workflow: record -> flag -> plot -> judge -> repair -> re-run.

 - Log every step: scan (1080 values), steer, speed, x, y, theta,
   front range, collision flag, time.
 - Flag: collisions (and the 2 s before), near-misses, steering flips,
   stuck/slow moments, centreline disagreement (if P3 available).
 - Plot: polar scan, bubble, all gaps in colour, chosen heading arrow,
   and the car on the map.
 - Judge: arrow into a real continuation of the track = rule was right
   (the crash was speed or bubble). Arrow into a wall pocket, the
   outside of a hairpin, or an opening past the corner = gap-selection
   failure.
 - Only gap-selection failures count for the two documented cases.

PART 8. RISKS AND PREVENTION
---------------------------------------------------------------------
 - AutoDRIVE slot comes too late      -> request in week 1, test week 2
 - Controller needs code change for AutoDRIVE -> keep scan-only and
   fully parameterised; changes go into configs or the sim wrapper
 - Repair fixes a corner but slows laps -> always compare on identical
   starts, and make the repair conditional if needed
 - Only crashes are counted as failures -> also replay saved scans
 - Metric/schema changes late         -> keep raw per-step data so the
   CSV can be regenerated
 - Tuning on one start only           -> use several start poses
 - Overwriting results                -> one file per run, never edit raw
 - Forgetting to record parameters    -> commit a yaml + tag per version
 - Python/pip confusion               -> python -m pip, activate f1env
